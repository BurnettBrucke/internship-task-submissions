# Query and Performance Review

## Overview

The Query and Performance Review was performed after completing the testing phase.

The review focused on:

- Identifying possible N+1 queries
- Reviewing `select_related()`
- Reviewing `prefetch_related()`
- Reviewing `count()`, `exists()`, `values()` and `values_list()`
- Inspecting SQL generated by important QuerySets
- Documenting one before-and-after optimization

> No code changes were made during this review. The existing QuerySets were inspected and documented.

---

## 1. N+1 Query Review

The following pages were reviewed for possible N+1 query problems:

| Page | Relationships Reviewed | Result |
|---|---|---|
| Student List | Department, Enrollments, Courses | Optimized |
| Admin Dashboard | Department, Enrollments, Courses | Optimized |
| Admin Dashboard | User, Profile, Requested Course | Optimized |
| Trainer Dashboard | Student, Course | Optimized |
| Student Dashboard | Course, Mark History, Updated By | Optimized |

### Result

No obvious N+1 query pattern was identified in the reviewed pages.

The required related data is loaded using `select_related()` and `prefetch_related()`.

# 2. `select_related()` Review

`select_related()` is used for single-valued relationships such as `ForeignKey` and `OneToOneField`.

### Reviewed usage

```python
.select_related("department")
```

```python
.select_related(
    "profile",
    "profile__requested_course"
)
```

```python
.select_related(
    "student",
    "course"
)
```

```python
.select_related("course")
```

### Result

The generated SQL confirmed that these relationships are loaded using SQL joins.

For example:

```sql
INNER JOIN "students_course"
ON ("students_enrollment"."course_id" = "students_course"."id")
```

This prevents additional queries when the related object is accessed.

---

# 3. `prefetch_related()` Review

`prefetch_related()` is used for reverse and multi-valued relationships.

### Reviewed usage

```python
.prefetch_related(
    "enrollments__course"
)
```

and:

```python
.prefetch_related(
    "mark_history__updated_by"
)
```

These match the relationships accessed by the templates.

For example, the Student Dashboard accesses:

```django
{% for history in enrollment.mark_history.all %}
    {{ history.updated_by.username }}
{% endfor %}
```

The nested prefetch handles both `mark_history` and `updated_by`.

### Result

No obvious N+1 issue was identified in the reviewed reverse relationships.

> `prefetch_related()` executes additional queries separately, so those queries do not appear in the main SQL generated by `queryset.query`.

# 4. Query Method Review

## `count()`

`count()` is used where the actual number of records is required.

Examples:

```python
total_students = students.count()
```

```python
total_courses = courses.count()
```

```python
total_students = assigned_students.count()
```

These are appropriate because the dashboards display numeric totals.

---

## `exists()`

`exists()` is useful when only the existence of a record is required.

The reviewed dashboard counters require the actual number of records, so replacing those `count()` calls with `exists()` would not provide the required result.

### Result

No `count()` replacement with `exists()` was required.

---

## `values()` / `values_list()`

`values()` and `values_list()` are useful when only specific database fields are required.

The reviewed templates require complete model instances and related objects, for example:

```django
{{ student.department.name }}
```

and:

```django
{{ enrollment.course.course_name }}
```

Therefore, changing these QuerySets to `values()` or `values_list()` was not necessary.

# 5. SQL Inspection

Five important QuerySets were inspected.

## 1. Student List

The generated SQL included:

```sql
LEFT OUTER JOIN "students_enrollment"
LEFT OUTER JOIN "students_course"
LEFT OUTER JOIN "students_department"
```

It also used:

```sql
COUNT(DISTINCT "students_enrollment"."course_id")
```

### Result

Search, relationships and course counting are handled at database level.

---

## 2. Admin Dashboard — Students

The optimized SQL included:

```sql
COUNT(DISTINCT "students_enrollment"."course_id")
```

and:

```sql
LEFT OUTER JOIN "students_department"
```

### Result

Department data is joined directly and course counts are calculated by the database.

---

## 3. Admin Dashboard — Trainers

The generated SQL joined:

```text
User
 ↓
UserProfile
 ↓
Requested Course
```

using:

```sql
INNER JOIN "students_userprofile"
LEFT OUTER JOIN "students_course"
```

### Result

The `select_related()` configuration is working as intended.

---

## 4. Trainer Dashboard — Assigned Enrollments

The generated SQL joined:

```text
Enrollment
 ↓
Course
 ↓
Student
```

and filtered enrollments according to the trainer's assigned courses.

### Result

Student and course data are loaded through joins instead of separate queries for each enrollment.

---

## 5. Student Dashboard — Enrollments

The generated SQL included:

```sql
INNER JOIN "students_course"
```

because of:

```python
.select_related("course")
```

### Result

Course information is loaded together with the enrollment.

The `mark_history__updated_by` prefetch is executed separately and therefore is not visible in this main SQL query.

# 6. Before vs After Optimization

## Admin Dashboard — Student QuerySet

### Before

```python
students = Student.objects.select_related(
    "department"
)
```

The query loaded students and departments but did not calculate the course count.

### After

```python
students = Student.objects.select_related(
    "department"
).prefetch_related(
    "enrollments__course"
).annotate(
    course_count=Count(
        "enrollments__course",
        distinct=True
    )
).order_by("name")
```

### Main improvement

The database now calculates the unique course count:

```sql
COUNT(DISTINCT "students_enrollment"."course_id")
```

The template can directly use:

```django
{{ student.course_count }}
```

### Result

Course counting is handled at database level instead of requiring separate application-level counting for each student.

# 8. Conclusion

The Query and Performance Review is complete.

### Findings

* No obvious N+1 queries were identified in the reviewed pages.
* `select_related()` is correctly used for single-valued relationships.
* `prefetch_related()` is correctly used for reverse/multi-valued relationships.
* `count()` is used where actual record totals are required.
* `exists()`, `values()` and `values_list()` were not required for the reviewed QuerySets.
* Five important QuerySets were inspected through generated SQL.
* Database-level aggregation is used for student course counts.
* The reviewed QuerySets are structured to reduce unnecessary database queries.
